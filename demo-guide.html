problem statement

The problem this project solves

the reality of software pipelines today
Every software team runs a CI/CD pipeline. Every pipeline breaks — multiple times a day. When a test fails, this is what happens today: 1. Pipeline runs → test fails → pipeline stops 2. A notification goes to a developer 3. Developer stops what they are doing 4. Developer opens the logs and reads the error 5. Developer figures out which file has the bug 6. Developer writes a fix 7. Developer pushes the fix 8. Pipeline runs again Time lost per incident: 15 to 60 minutes Incidents per team per day: 3 to 10 This is repetitive, interruptive, and entirely manual.
why this is a problem worth solving
Most pipeline failures are not complex. Common causes: → A typo or accidental method call (like .upper() on the wrong variable) → A missing import → A wrong variable name → A formatting issue These bugs take 2 minutes to fix — but 20 minutes to find, context-switch to, fix, and re-verify. An AI that can read error logs, understand code, and write a fix eliminates the entire middle section of that process. The developer sees: pipeline failed → pipeline fixed. Nothing in between.
what this project demonstrates
This project builds an AI-driven CI/CD pipeline using: → A Python Todo application (the codebase being tested) → pytest (the test suite that catches bugs) → GitHub Actions (the CI/CD pipeline runner) → OpenAI GPT-4o (the AI that reads errors and writes fixes) → autofix.py (the agent that connects them) The demo scenario: A developer pushes code with a bug — .upper() accidentally added to a method. This causes one test to fail: Expected "Buy groceries" but got "BUY GROCERIES" The AI agent: → reads the pytest failure output → identifies the exact line with the bug → removes .upper() → commits the fix → pipeline re-runs and passes The developer did nothing after the initial push.
project file structure
Demo 1/ ├── todo.py ← the Python app being tested ├── todo_BROKEN_for_demo.py ← same app with the .upper() bug — used to trigger the demo ├── test_todo.py ← 7 pytest tests that catch the bug ├── requirements.txt ← just pytest ├── autofix.py ← the AI agent: reads error → calls OpenAI → writes fix └── .github/ └── workflows/ └── autofix.yml ← the pipeline: runs tests → triggers agent → pushes fix

understanding your options

Two approaches — which one are you using?

There are two ways to run this demo. The concept is identical in both — AI reads the test failure, fixes the code, commits it. The difference is who runs the pipeline and who provides the agent.

⚙ Approach A — Harness Platform
  • → Pipeline runs on Harness CI
  • → Agent is the Harness Autofix Agent (prebuilt, from Marketplace)
  • → Your file: .harness/pipeline.yaml
  • → Requires a Harness account + 5 secrets
  • → This is the official Harness demo
⚙ Approach B — GitHub Actions + OpenAI
  • → Pipeline runs on GitHub Actions
  • → Agent is your own autofix.py script
  • → Your file: .github/workflows/ci.yml
  • → Requires only 1 secret (OpenAI API key)
  • → This is a custom / DIY version of the same concept
is Approach B "custom Harness"?
Yes — Approach B is a DIY version of what Harness's Autofix Agent does. The concept is the same: AI reads test failure → identifies bug → writes fix → commits → pipeline goes green The difference is who built the agent: Approach A: Harness built it → you install it from their Marketplace Approach B: You built it → autofix.py is your own agent If you are demoing this AS a Harness product: use Approach A (.harness/pipeline.yaml) If you just want to prove the concept cheaply: use Approach B (ci.yml + autofix.py)

autofix.yml — one file, does everything

After testing different approaches, the final solution is a single autofix.yml that handles the full flow: run tests → detect failure → call OpenAI → commit fix — all in one workflow triggered by every push.

.github/workflows/autofix.yml — full breakdown
Triggers on: every git push to main Steps: 1. Checkout ref: main with GITHUB_TOKEN ↑ checks out the branch, not a commit SHA — critical for the push to work 2. Set up Python 3.12 + pip install -r requirements.txt 3. Run tests (id: run_tests, continue-on-error: true) set -o pipefail pytest test_todo.py -v --tb=short 2>&1 | tee test_output.txt ↑ pipefail captures pytest exit code | tee shows live output AND saves to file 4. errors encountered along the way — and how they were fixed

Lessons learned building this workflow

error 1 — AI Autofix step was always skipped
Problem: pytest test_todo.py | tee test_output.txt The pipe exit code comes from tee (always 0), not pytest. So GitHub Actions thought tests passed even when they failed. run_tests.outcome was always 'success' → AI Autofix never triggered. Fix: shell: bash set -o pipefail pytest test_todo.py -v --tb=short 2>&1 | tee test_output.txt pipefail makes the pipe use pytest's exit code, not tee's.
error 2 — push rejected "remote contains work you do not have"
Problem: checkout ref: github.event.workflow_run.head_sha Checking out a commit SHA puts git in "detached HEAD" mode. You are not on any branch — git does not know where to push. git push HEAD:main → rejected because remote has moved ahead. Fix: checkout ref: main Checks out the actual branch. You are ON main. git push origin main → clean push, no rejection.
error 3 — test output not visible in Actions log
Problem: pytest > test_output.txt 2>&1 cat test_output.txt cat always exits 0 → step outcome was always 'success'. Also output was buffered, not visible until after the step ended. Fix: pipefail + tee streams output live to the Actions log AND saves to test_output.txt at the same time. Exit code comes from pytest, not tee or cat.

if something goes wrong

Troubleshooting

Command not found: python3
Run sudo apt install python3 — but this is already installed on Kali by default. Try which python3 to confirm.
pip install fails with "externally managed environment"
This means you skipped step 03. You must create the virtual environment first with python3 -m venv .venv and then use .venv/bin/pip, not the system pip.
.venv/bin/pytest: No such file or directory
pytest wasn't installed. Run step 04 again: .venv/bin/pip install -r requirements.txt
Tests all pass even after copying the broken file
The copy may not have worked. Confirm with grep upper todo.py — if you see .upper() on line 9, the broken version is active. If not, run the cp command from step 06 again from inside the project folder.
sed command doesn't fix the file
Make sure you are inside the project folder when you run it. Run pwd — the output should end in Demo 1. Also verify the broken file is active: grep upper todo.py.
Want to reset and run the whole demo from scratch
Run: cp todo_BROKEN_for_demo.py todo.py to re-introduce the bug, or sed -i 's/text.strip().upper()/text.strip()/' todo.py to fix it again. The .venv only needs to be created once.
